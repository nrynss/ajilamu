### Probe cost

`TestR3ProbeCostOnResume` resumed three recorded takes and measured six ffprobe invocations.
Each resumed take costs two spawns. The first spawn is the new probe in `takeFileUsable`.
The second is the existing `media.Duration` call inside `RepairLine`.
A large dub therefore adds about two ffprobe processes per recorded segment on every resume.
The loop runs them one segment at a time, so the wall time grows with the segment count.

## Findings

| # | Sev | Where | What | Pin | Mutation |
|---|---|---|---|---|---|
| 1 | M | `internal/fit/loop.go:261-264` | `readSegmentRecord` deletes the recorded take whenever `takeFileUsable` returns false. `takeFileUsable` also returns false when the probe itself fails, including a cancelled or expired context. A cancelled run therefore deletes the completed take it was probing. | `TestR3CancelledProbeDeletesValidTake`, `TestR3TimeoutDuringProbeDeletesValidTake`, `TestR3RunCancelledDuringProbeDeletesTake` | Adding the `ctx.Err()` guard flips all three pins from fail to pass, and the four shipped re-render tests still pass. |

### Finding 1 detail

`takeFileUsable` calls `media.Duration` with the run context.
`media.Duration` returns a context error when the context ends during the probe.
`takeFileUsable` maps every error to false.
`readSegmentRecord` then calls `discardTakeFile`, which removes the take.
The take is complete and decodable, so the deletion is not intended.
The run reaches this path because `Run` checks `ctx.Err()` before the segment,
then `repairSegment` probes before `RepairLine` checks the context again.
A cancel or a deadline that lands inside the probe deletes the take.
The next resume then re-renders that segment, which defeats the task contract.

`TestR3RunCancelledDuringProbeDeletesTake` drives the whole `RunPipeline` with a 300ms deadline
and a slow ffprobe. The run ends with `context deadline exceeded`, and the take is gone.

The fix is to remove the take only when the probe failure is about the file, not the context.

```go
	if !takeFileUsable(ctx, rec.Result.ChosenTake.File) {
		if ctx.Err() == nil {
			discardTakeFile(rec.Result.ChosenTake.File)
		}
		return LineResult{}, false
	}
```

## What I did not file

- **The probe follows the record's take path outside the work directory.**
  `TestR3SymlinkAtTakePath/valid target outside` adopted a symlink target outside the work dir,
  and `TestR3TakePathEscapesWorkDir/unusable outside file is deleted` deleted an outside file.
  The record is the loop's own output, and round 2 already judged a hand-edited record out of
  contract. The loop never writes a record that names an outside path. I did not file it.
- **The replay path adopts a decodable take whose length disagrees with the record.**
  `TestR3TruncatedAfterHeader/replay adopts` reported the stale 2000ms fit for a 3ms file,
  and `TestR3WrongLengthTake/replay trusts the record` did the same for a 4000ms file.
  `writeTake` writes the whole payload in one call and the loop writes the record after the take,
  so a single crash leaves a truncated take with no record, not with a record. I did not file it.
- **A non-empty directory at the take path aborts the run.**
  `TestR3DirectoryAtTakePath/nonempty` measured `tts refuses to overwrite`.
  The loop never creates a directory at a take path, so I treat it as tampering.
- **A line interrupted mid-attempt with no record still aborts.**
  The removal in `discardTakeFile` is record-scoped. Rounds 1 and 2 already declined this case,
  and the Done-when stops after a completed take.
- **The resumed run reports zero cost for replayed lines.**
  Rounds 1 and 2 declined it. The ledger holds the first run's charges.
- **Removing the size check survives the pins.**
  Mutation M1 removed `info.Size() == 0` and every empty-take pin still passed,
  because the probe rejects a zero-length file on its own. The size check is redundant, not wrong.
- **Removing the regular-file check survives the FIFO pin.**
  Mutation M9 removed `!info.Mode().IsRegular()` and `TestR3FIFOAtTakePath` still passed,
  because a FIFO reports size zero and the size check rejects it first. The stat-first ordering
  is what prevents the hang.
- **The `InitialTake` path does not return the record verbatim.**
  `RepairLine` regenerates `RepairDetail` and `NotificationCopy` from the fresh measurement.
  The take, the text, and the fit match the record. I treat the copy as derived, not replayed.
