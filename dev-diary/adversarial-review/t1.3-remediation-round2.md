## The design decision behind findings 1 and 2

Findings 1 and 2 asked one question. A `timeline_state` row is now a **full snapshot** of one
segment at one commit, never a delta.

I chose the snapshot because it makes the table, the sorting key, the comments and the read
agree. A snapshot per (dub, language, commit, segment) is unique, so the sorting key is the
natural identity and needs no extra id. Two edits to one segment inside one commit collapse
to that commit's final state, which is the answer a reader wants. Every surviving row is
complete, so `argMax` over an ancestry set never returns a DEFAULT for a field the newest
ancestor commit did not touch.

A delta design would need a unique id in the key and a read that folds deltas forward across
the ancestry, per column. That read is far harder to write correctly and impossible to
express as one view, and T4.5 would carry the risk.

Two changes back the decision. The engine is now `ReplacingMergeTree(ingested_at)`, so the
later write for one commit and segment wins on the server clock rather than on arrival order.
The file also ships `timeline_at_commit`, a parameterized view that runs the recursive
ancestry walk and the per segment `argMax`. T4.5 calls that view rather than rebuilding the
query, so the prescribed read and the shipped read cannot drift apart.
