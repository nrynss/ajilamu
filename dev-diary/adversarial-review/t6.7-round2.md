## Done condition

**The done condition holds for one edit at a time.** A boundary drag and a command confirmation
each write one commit, one action and one timeline snapshot. The History tab shows both. The
edit survives a reload. The condition fails when a run commit lands concurrently, because the
head timeline drops the edit. Round-two H1 covers that case.

## Residue against round one

**Round one H1 is closed for two edits of one dub.** The edit lock makes the head read and the
append atomic per dub. Twelve concurrent boundary edits and twelve concurrent commands chain.
The pin passes. The mutation removes the lock and the fork returns. Zero residue for the exact
case round one named.

**The invariant round one named is open for the other writers.** Round one H1 said the head read
and the append were not atomic per dub. The fix makes them atomic for edits only. The run and
re-render writers still read and append without that lock. Measurement shows the fork. I filed
it as round-two H1.

## Disclosed runRecorder residue, judged

The remediation disclosed that `runRecorder.persist` reads the head the same way for run and
re-render commits and takes no edit lock. I judged it on measurement, not on the disclosure.

The residue is real. One run commit raced against one boundary edit forked the DAG in 14 of 20
trials. The edit answered 201 and left the head timeline. The 24-edit case forked in 6 of 6
trials. The failure mode is exactly round one H1, on a writer the fix does not cover.

The fix is small and the pattern exists. A shared per-dub commit lock across `EditsHandler` and
`runRecorder.persist` closes it for both the run and the re-render path.
