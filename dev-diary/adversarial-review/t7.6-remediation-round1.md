## Finding 1, the headless favicon

Observers. The backend was the current `./cmd/ajilamu` binary, built to `/tmp/t76r/bin/ajilamu`.
It served a pre-fix build at `/tmp/t76r/build-prefix` through `AJILAMU_FRONTEND_DIR`. That build is
`web/build` with the `rel="icon"` link removed. The logging reverse proxy listened on port 18090
and forwarded every request to the binary on port 18092. The browser was
`google-chrome-stable` 152.0.7977.82. Every run used a fresh profile and an empty disk cache.

The proxy observed these headless runs of the pre-fix build.

| Mode | Proxy requests | 404 | Favicon line |
|---|---:|---:|---|
| `--headless` | 15 | 1 | `GET /favicon.ico -> 404 Not Found 19 bytes` |
| `--headless=new` | 15 | 1 | `GET /favicon.ico -> 404 Not Found 19 bytes` |
| `--headless=old` | 15 | 1 | `GET /favicon.ico -> 404 Not Found 19 bytes` |
| `--headless --dump-dom` | 11 | 1 | `GET /favicon.ico -> 404 Not Found 19 bytes` |
| `--headless --screenshot` | 15 | 1 | `GET /favicon.ico -> 404 Not Found 19 bytes` |

CDP. A Node client attached to the page target with `Network.enable`. It then navigated to
`http://127.0.0.1:18090/` and collected 30 network events. It recorded
`Network.requestWillBeSent GET http://127.0.0.1:18090/favicon.ico` and
`Network.responseReceived status 404` for request id `1512365.20`. The proxy logged the same
request.

Fixed build. The same binary served `web/build`, which carries the data URI icon. One
`--headless=new` run made 14 requests with zero 404 and no favicon request. That matches the
handoff's headed-load count.

Conclusion. Headless Chrome fetches the favicon. The page-level CDP client reports it. Both
handoff claims were false. The logging proxy advice holds.

## Finding 2, the lockfile bytes

Before. `web/package-lock.json` held 83 entries at lockfile version 3. Only 25 carried `resolved`
and `integrity`. Those 25 are the optional platform packages that do not install on linux-x64. The
57 packages that `npm ci` installs carried neither field.

Regeneration. I copied `web/package.json` into an empty `/tmp/t76r/lockgen`. I ran
`npm install --package-lock-only --cache /tmp/t76r/npmcache-fresh`. The command exited 0 and
printed `up to date, audited 58 packages in 10s`. The copied `package.json` was unchanged.

After. The new lockfile holds the same 83 entries and the same 82 package paths. Every one of the
82 non-root entries carries `resolved` and `integrity`. The root entry carries neither, which is
npm's shape for the project itself. The 82 versions are identical to the old lockfile, with zero
differences. `engines.node` stays `>=26 <27` and the devDependencies are unchanged. The file is
valid JSON.

Cold install. I copied `package.json` and the new lockfile into `/tmp/t76r/ci-copy`. I ran
`npm ci --cache /tmp/t76r/npmcache-ci` with an empty cache. It exited 0 and printed
`added 57 packages, and audited 58 packages in 2s`. I never ran `npm ci` inside `web/`.

Versions. I walked every installed `package.json` under `web/node_modules` before the change and
under `/tmp/t76r/ci-copy/node_modules` after. Both sets hold 57 name and version pairs. The sets
are identical, with no additions and no removals.
