# T4.5 live ClickHouse probe

Verdict: REMEDIATE

Counts: C 0, H 1, M 2, L 4

Prior-round residue: Round 1 approved T4.5 against `httptest` mocks that served hardcoded
payloads. Its handoff named a live probe of the real view as unowned work. This probe is
that b-track. It reproduces the round 1 ground on a real server, then goes past it.

## Scope

I ran ClickHouse 26.8.2.7 two ways. First as `clickhouse local --path` over a persistent
directory. Then as a real `clickhouse server` process on `127.0.0.1:18123`, driven over the
same HTTP protocol `postClickHouse` uses. Both loaded `sql/schema.sql` verbatim through
`--queries-file`. Every statement under test came out of the shipped source by AST
extraction, not by retyping. `ReplayAt` and `commitAncestry` were lifted verbatim into a
scratch package and diffed against `internal/ledger/history.go` before use.

`clickhouse local` and a self-hosted server are not the hosted ClickHouse Cloud instance
this project targets. Cloud runs its own settings profile, its own storage tier, and its own
merge scheduling. Findings 1, 3, and 5 all turn on server settings or merge timing. A Cloud
run could move their numbers. I state below which claims this probe closes and which it
leaves open.

## Independent evidence

I extracted `insertTimelineState`, `selectTimelineAt`, and `selectBranchCost` from
`internal/ledger/history.go` by parsing the Go AST. The extractor wrote 193, 139, and 605
bytes. Every query below ran those bytes.

I lifted `ReplayAt`, `commitAncestry`, `cmpTimelineSegment`, `validateHistoryQuery`,
`TimelineSegment`, and `Commit` into a scratch package by AST copy. A line diff of the
lifted `ReplayAt` and `commitAncestry` against `internal/ledger/history.go` showed no
difference.

`sql/schema.sql` loaded into `clickhouse local` and into a real server with exit code 0. Both
created twelve objects, including the parameterized view `timeline_at_commit`.

The production `selectTimelineAt` executed. The parameterized view accepted `--param_dub_id`,
`--param_language`, and `--param_commit_id` as view arguments.

Output at heads c1, c2, and c3 was byte identical to `viewAtRoot`, `viewAtChild`, and
`viewAtFork`. I extracted those three constants from `history_test.go` by AST and compared
with `diff`. The comparison passed in `clickhouse local` and again over real HTTP.

`selectBranchCost` returned `main` and 0.0003 at c2. It returned `alt` and 0.0006 at c3. The
sibling's charge stayed out of each sum.

The pre-3c1035e statement raised `Code: 125 INCORRECT_RESULT_OF_SCALAR_SUBQUERY` at absent
head c9 on the real server. The shipped statement returned an empty branch and a zero cost
at the same head. The `any(branch)` fix holds.

A four-deep chain matched replay at all four heads. A fork off a fork matched replay at all
six heads. A commit carrying `version_seq` 9 after a chain of 3 matched replay.

Two branches reused `version_seq` 3 on the same segment with different text. The head of the
alt-of-alt branch inherited the alt row, not the main row. `version_seq` did not select the
ancestor set.

I wrote one snapshot at a child commit carrying `version_seq` 1 while its commit row carried
2. The view returned the ancestor's row. `ReplayAt` returned the child's row. The two
programs disagreed.

I built a three-commit chain with all three snapshots tied at `version_seq` 1. The view
returned the newest commit's row across twelve consecutive runs. After `OPTIMIZE TABLE
timeline_state_raw FINAL`, the same query on the same rows returned the oldest commit's row.

I checked 100 tied result rows across 40 parts at `max_threads 8` for field splitting. Every
row drew all eight fields from one source row. Per-column `argMax` did not mix two rows.

The production INSERT raised `Code: 469 VIOLATED_CONSTRAINT` on an inverted slot, on an empty
slot, and on a negative `segment_index`. The named constraints were `slot_is_positive` and
`segment_index_is_real`. Zero rows landed.

I sent one identical snapshot five times. The `timeline_state` view held one row.
`timeline_at_commit` returned one row.

I sent two different edits to one commit and segment, then replayed the first. The view
returned the stale text. `ReplacingMergeTree(ingested_at)` keeps the newest server clock, and
the replay carried the newest one.

That resurrection is not reachable through the shipped writer. `Queue.entries` sorts by a
zero-padded sequence filename. `Queue.Flush` returns at the first failing batch and removes
nothing after it. `EnqueueJSON` enqueues and then drains the whole queue. A later edit cannot
land while an earlier one is still journalled.

`cost_usd` reported `Decimal(38, 14)` through the view and through the branch cost statement.

A charge of 0.0001 units at 0.0000000001 per unit serialized as `0.00000000000001`. The
output carried no quotes and no scientific notation.

I summed 5000 distinct charge rows at the smallest representable price. The statement
returned `0.00125025005`. That equals the exact decimal sum. No float drift appeared.

A charge of 99999999999999.9999 units at 99999999.9999999999 per unit serialized as
`9999999999999999980000.00000000000001`. Forty such rows summed to
`399999999999999999200000.0000000000004`. No overflow error appeared.

The shipped `branchCostRow` decoded that 36-digit value. `json.Number.String()` returned the
literal unchanged. The value exceeds float64 precision, and `history.go` never converts it.

With `output_format_json_quote_decimals=1` the cost arrived as `"0.0003"`. The shipped struct
still decoded it, because Go accepts a quoted number into `json.Number`.

With `output_format_json_quote_64bit_integers=1` the view returned `"start_ms":"1100"`. The
shipped `timelineAtRow` failed to decode it. The runtime default is 0 on 26.8.2.7 in both
local and server mode. The setting description still states that integers are quoted by
default.

A commit whose parent id named a missing row terminated in 0.04 seconds. It returned the
head's own rows. `commitAncestry` breaks on a missing commit and agrees.

A self-referencing parent and a two-commit cycle both raised `Code: 306`. Neither hung.
`timeline_at_commit` failed after 1.33 seconds. `selectBranchCost` failed after 7.29 seconds.

I built a 1300-commit chain. `selectTimelineAt` returned rows at depth 1000 and raised
`Code: 306` at depth 1001. Timings were 0.18s at depth 100, 0.79s at 500, and 1.53s at 1000.

`selectBranchCost` on the same chain took 1.49s at depth 100, 7.49s at depth 500, and 14.96s
at depth 1000. The ledger HTTP client allows 30 seconds per request.

Passing `max_recursive_cte_evaluation_depth=5000` in the URL made depth 1300 return rows in
1.78 seconds. The ceiling is a per-query setting the client can set.

`ReplayAt` returned the correct state at depth 1300 and on the cycle. The view returned
Code 306 for both.

Two dubs shared the commit ids `sh1` and `sh2` with different branches and different text.
Queries for `dT1` returned only tenant A rows. Queries for `dT2` returned only tenant B rows.
Branch labels came back as `main` and `trunk` correctly.

One dub carried `ml` and `hi` snapshots on the same commit. Each language query returned its
own row. Branch costs came back as 0.11, 0.33, and 0.22 with no bleed.

The recursive ancestry set for c2 was `['c2','c1']`. The empty string never entered it, so a
whole-pass charge cannot join an ancestry sum.

`go test ./internal/ledger -count=1` passed. `git status --short` reported no changes before
this file. Those checks do not prove the query contract.

## What this probe closes and what it leaves open

Closed. The shipped statements execute on a real ClickHouse 26.8.2.7 over the real HTTP
protocol. The parameterized view binds three query parameters as view arguments. Output at
the three fixture heads matches the round 1 constants byte for byte. The two schema
constraints fire. Identical resends collapse under `FINAL`. Decimal cost survives
serialization and Go decoding exactly at both extremes. Cross-dub and cross-language
isolation holds. `version_seq` does not select the ancestor set on a fork, on a fork off a
fork, or across branches that reuse a value.

Open. The depth ceiling, the query timings, and the JSON quoting default all depend on the
server profile. I measured them on a local server with small parts and a warm page cache.
ClickHouse Cloud may set a different `max_recursive_cte_evaluation_depth`, and it will
certainly show different timings. The merge that flipped the tie result was forced by
`OPTIMIZE`. On Cloud the same flip would arrive on the background merge schedule, at a time
nobody chose. I did not test a replicated table, a distributed read, or a Cloud settings
profile.

Not tested. No production code calls `RecordSegmentState`, `TimelineAt`, `ReplayAt`, or
`CompareBranches` yet. Every reachability claim above concerns the API surface, not a live
call path.

I removed the scratch database, the scratch server, and every scratch binary after
measurement.

Residue: Findings 1 through 7 are open.
