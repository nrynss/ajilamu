## Findings

| Where | What | Pin | Mutation |
|---|---|---|---|
| M1 · `internal/tts/catalog.go` lines 113 to 132 and lines 92 to 111 | `voiceLister` reads `c.lister` under a read lock, releases it, then builds a client. Two refreshes that both see nil each call `newProductionVoiceLister`. The loser's client is overwritten in `c.lister` and never closed, so its gRPC connection leaks. After the client exists, every concurrent refresh still issues its own `voices.list`. The comment says the code builds the production one once, and it does not. T7.5b mounts two pickers, each with its own refresh button and its own `refreshing` guard. Two quick clicks reach the route at once. | In a scratch copy I ran `TestT77ConcurrentBuildRace` with eight concurrent `Refresh` calls against a counting build. It logged `client builds = 8, ListVoices calls = 8`. `TestT77ConcurrentRefreshFetchesTwice` fired five concurrent POSTs at the mounted routes and logged five `voices.list` calls. `go test -race` reported no data race, so the defect is duplicate work and leaked clients. | A remediator serializes construction under a mutex and re-checks `c.lister` after the lock. Revert that guard and the first concurrent burst builds and leaks one client per refresh. |

Concrete fix for M1. Add the mutex field to `Catalog` and double-check after the lock.

```go
// buildMu serializes production client construction.
buildMu sync.Mutex

func (c *Catalog) voiceLister(ctx context.Context) (VoiceLister, error) {
	c.mu.RLock()
	lister, build := c.lister, c.build
	c.mu.RUnlock()
	if lister != nil {
		return lister, nil
	}
	c.buildMu.Lock()
	defer c.buildMu.Unlock()
	c.mu.RLock()
	lister = c.lister
	c.mu.RUnlock()
	if lister != nil {
		return lister, nil
	}
	if build == nil {
		build = newProductionVoiceLister
	}
	lister, err := build(ctx)
	if err != nil {
		return nil, nameMissingCredential(err)
	}
	c.mu.Lock()
	c.lister = lister
	c.mu.Unlock()
	return lister, nil
}
```

  handoff.
