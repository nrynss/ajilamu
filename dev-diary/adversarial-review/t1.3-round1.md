## False Positives

I checked one hypothesis and found no defect.

**`charges.kind` locked to three Enum8 values does not break a downstream insert.** The
vocabulary matches `internal/cost/cost.go` exactly, where `ChargeKind` defines
`ChargeSegment`, `ChargeTranslate` and `ChargeSynthesize` and nothing else. It matches T1.2,
which fixes the same three names. It also covers the real traffic. `observations.md` 2.4
records 9 uncosted Gemini calls, and the run breaks down as one segmentation call plus one
translation call for each of the 8 segments. Section 1 shows both repairs used `atempo`, so
no rewrite call fired. A future Gemini rewrite bills as `translate` and still sums
correctly. Rejecting an unknown kind at insert is the behaviour the ledger wants, so I
record no finding here.

## What I Confirmed Working

I list these so a remediator does not disturb them.

- The file names no database and carries no `ON CLUSTER` clause, no `SETTINGS` clause and no
  Cloud-only or local-only syntax. It created all four tables on Cloud 26.2.1.641 and on
  local 26.8.2.7 from one unmodified file.
- Running the whole file a second time succeeded on both servers and preserved existing rows.
- All 10 fixture take rows loaded. Segment 8 read back `delta_ms` of -2910 against
  `slot_ms` 7110 and `measured_ms` 4200, matching `testdata/expected/metrics.json`.
- The `delta_is_signed` constraint fired on both servers for an absolute value delta of 2910
  and for a one-sided delta of 0.
- The `peaks_are_sized` constraint fired for an array of length 10 and accepted lengths 0
  and 64.
- `takes` has no cost column. An insert naming `cost_usd` failed with
  `Code: 16 NO_SUCH_COLUMN_IN_TABLE`, so no writer can park a running total on a take.
- `charges.cost_usd` refused a direct write with `Code: 44 ILLEGAL_COLUMN` and computed
  100 units at 0.00003 as 0.003. `SELECT *` omitted it, as the comment claims.
- `units_are_positive` fired on units of -5.
- The `prior_by_speaker` projection exists and `EXPLAIN projections = 1` reported it usable
  for a language and speaker filter. The planner skipped it only because 10 rows fit one
  mark, which is correct behaviour.
- Every column T4.2, T4.6 and T4.7 name exists with a usable type. I found no missing column
  for those three tasks.
- The comments break none of the four house style rules. I parsed every comment line and
  found no semicolon, no em dash, no sentence over 30 words and no passive construction.

## Verification

I ran these checks myself. I sourced the gitignored `.env` inside each command and never
printed, echoed or wrote any credential. The commands below are described rather than
pasted, because pasting them would carry the secret.

**One.** I read `SELECT version()` from the Cloud HTTPS endpoint and got 26.2.1.641. I read
`clickhouse --version` from the extracted local binary and got 26.8.2.7.

**Two.** I listed `system.tables` on Cloud before touching anything. The service held exactly
one user table, `default.takes`, engine SharedMergeTree. `SHOW CREATE TABLE default.takes`
returned the validation-run shape and `SELECT count()` returned 8. This is the evidence
behind finding 1.

**Three.** I created the database `t13_review_r1` on Cloud and applied `sql/schema.sql`
unmodified with `clickhouse client --queries-file`. I passed the host on the command line
and let the client read the user and password from the environment. `system.tables` then
listed actions, charges, commits and takes, all SharedMergeTree, all partitioned by
`toYYYYMM(created_at)`, with the sorting keys the file declares. Cloud rewrote MergeTree to
SharedMergeTree on its own, exactly as the header says.

**Four.** I ran the same file a second time against the same database. It exited 0. I
repeated the whole create-then-rerun cycle on local 26.8.2.7 and it exited 0 there too, with
one row still in takes and one in charges afterwards.

**Five.** I generated 10 take rows from `testdata/expected/metrics.json` and
`testdata/segments.json` rather than from any sample the implementer supplied. That is 8
first attempts plus the two stretched repairs for segments 3 and 4. All 10 inserted. Reading
back segment by segment reproduced every slot, measurement and delta in the fixture,
including segment 8 at -2910 ms.

**Six.** I fired four negative pins at `takes`. An absolute value delta of 2910 for segment 8
failed `delta_is_signed`. A delta clamped to 0 failed the same constraint. A peaks array of
length 10 failed `peaks_are_sized`. An insert naming `cost_usd` failed with no such column.
The table still held exactly 10 rows afterwards. I repeated the first pin on local 26.8.2.7
and it failed there too.

**Seven.** I probed the enums. `charges.kind` of `rewrite` and `actions.author` of `system`
both failed with `UNKNOWN_ELEMENT_OF_ENUM` on both servers. `takes.repair` of
`ludicrous_speed` was accepted and read back, which is finding 6.

**Eight.** I built 17 charges rows from the fixture segment texts, one segmentation call plus
one translation and one synthesis call for each of 8 segments. Grouped by kind the totals
read 0.000067, 0.000067 and 0.0201. `SELECT *` returned 15 column names and omitted
`cost_usd`. I then re-sent the identical batch and watched the row count reach 34 over 17
distinct ids with the total at 0.040468. That is finding 2.

**Nine.** I wrote a four commit DAG with a fork, then compared three ways of selecting the
ancestors of the forked commit. The `version_seq` filter the comment recommends returned a
commit from the other branch. The branch filter lost the shared ancestors. Only
`WITH RECURSIVE` over `parent_commit_id` returned the right set. That is finding 3.

**Ten.** I wrote a `boundary_nudged` action on segment 8 and compared the JSON it stored
against what a direct query of `takes` returns for that segment. They disagree by 200 ms.
That is finding 4.

**Eleven.** I inserted a commit with an explicit `created_at` of 2099-12-31. Cloud accepted
it and `system.parts` grew a `209912` partition. That is finding 5.

**Twelve.** I ran the T4.7 queries. A personal prior grouped by speaker returned sample
counts of 8 and 2 with characters per second of 16.70 and 17.82. A population aggregate
across all owners returned 10 samples. `EXPLAIN projections = 1` reported `prior_by_speaker`
usable for a language and speaker filter.

**Thirteen.** I parsed every comment line in `sql/schema.sql` for the four house style rules
and found no violation.

**Fourteen.** One note that is not a finding. The Cloud HTTP query endpoint rejects the file
as a whole with `Code: 62 Multi-statements are not allowed`. The file loads correctly through
`clickhouse client --queries-file`. T4.1 will need to split the file on statement boundaries
if it applies the schema over HTTP.

**Fifteen.** I dropped `t13_review_r1` from Cloud. `system.databases` no longer lists it.
`default` still holds one table with 8 rows, untouched.
