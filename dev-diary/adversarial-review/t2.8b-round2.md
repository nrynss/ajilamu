### M1: The runner pin passes a constant tag

`TestPipelineRunnerLanguageWiring` starts a run with `Language: "ml"`
(`cmd/ajilamu/main_test.go:698`). `resolveRunLanguage` maps `ml` onto `ml-IN`. The test then
asserts `factoryLanguage == "ml-IN"` (`cmd/ajilamu/main_test.go:707-709`).

Any implementation that passes the literal `"ml-IN"` satisfies that assertion. The test cannot
tell the resolved tag from the constant. It also supplies its own `newSynthesizer` closure
(`cmd/ajilamu/main_test.go:689-692`), so it never observes the production closure at
`cmd/ajilamu/main.go:429-431`.

Mutation D shows the gap. `Run` calls `p.newSynthesizer("ml-IN", charges)` at
`cmd/ajilamu/main.go:452`. Both committed tests pass. An `es-ES` run would carry `es-ES` into the
prompt and `ml-IN` into the voice. The API already accepts any code through the `language` query
(`internal/api/run.go:521`), so the bad path is reachable today. T7.5b plans to send full tags.

Mutation C is the exact mutation the round one review named. It changes the production closure to
build `ml-IN`. The committed suite passes, because no offline test reaches `newPipelineRunner`
with a real config. The reachable fix is a second case that uses a code whose tag differs from
`ml-IN`.

```suggestion
	cases := []struct {
		name     string
		language string
		tag      string
		target   string
	}{
		{name: "create screen code", language: "ml", tag: "ml-IN", target: "Malayalam"},
		{name: "full tag", language: "es-ES", tag: "es-ES", target: "es-ES"},
	}
```
