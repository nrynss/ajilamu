### 7. The attempt mismatch

The route response reports attempt 2 while the fit loop chose attempt 1. That is the
documented T6.5a convention, not a defect. `rerenderResult` overwrites the fit
attempt with the file's try number. The ledger sorts takes by that number.
`DetailsTab.svelte` labels each take `try N`. The ledger, the file name and the take
list therefore agree.

The remediator's reason is imprecise for production. The test seam maps every
attempt onto one file. The production `rerenderTakePath` extends the try number per
attempt, so the offset equals the count of earlier takes. The effect is the same and
no consumer needs the fit attempt number. I file nothing here.
