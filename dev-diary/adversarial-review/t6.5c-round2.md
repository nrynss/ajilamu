## What I measured

### 1. The symlink escape

| Probe | Status | Body |
|---|---|---|
| Link inside the root to an outside file | 404 | `404 page not found`, 19 bytes |
| Link to `/etc/passwd` | 404 | `404 page not found`, 19 bytes |

The outside file is 4096 bytes. `/etc/passwd` is 2168 bytes. Neither body carries a
byte of the target. The server served no outside content.

I probed more shapes on the same server.

| Probe | Status |
|---|---|
| Relative link that escapes the root | 404 |
| Link chain inside the root to outside | 404 |
| Project directory symlink to outside | 404 |
| Language directory symlink to outside | 404 |
| Relative link inside the root | 200 |
| Absolute link inside the root | 404 |

The last row is conservative. `os.OpenInRoot` refuses an absolute link even when the
target sits inside the root. The app writes takes as regular files, so no real take
has that shape. I record it as a note, not a finding.

## Handoff check

The handoff matches my measurements for the route, the resolver, the 200, the range
answer, the fixture bundle, both browser controls and both commands. Two wording gaps
stay, and both are non-blocking.

First, the handoff does not mention the symlink guard. It says the handler requires
the joined path to stay inside the root. That sentence covers the lexical check only.

Second, the handoff says the page never sends the server path to the browser. The
ledger payload still carries the absolute `take.file`, and the DOM still shows it in
`data-take-file`. That exposure predates this patch. The audio URL carries the
basename only.

The route also serves any regular file in the work directory, not only takes. I
fetched a record and got 200 with `application/json`. The workspace payload already
carries the same line text and takes, so I do not file it.
