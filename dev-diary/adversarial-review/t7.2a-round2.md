## Comment accuracy

and a pin-copying bypass passes it while failing `TestOnlyClientPinsServerSettings`.

P1 measured the second claim. The pin-copying bypass passed the decode test and failed the
guard. M3 to M6 measured the first claim for each reader. Each unpinned bypass failed the
decode test. The comment is accurate.

P2 shows the guard limit. A reader that calls a second `client.go` function which applies both
pins passes every shipped test and my structural probe. P2 does not copy a pin into a reader,
so it does not contradict the comment. Round 1 judged this limit acceptable, and I agree.
An AST guard is more rigor than this repository uses.

## What I did not file

- **Guard limit.** P2 shows a second `client.go` pin function passes both shipped tests.
  Round 1 measured the same class and judged it acceptable. The guard catches the literal
  copy that caused this bug, which is the realistic failure mode.
- **Helper comment reach.** The comment at `client.go:232` says every reader decodes `UInt64`
  or `int64`. `branchCostRow` holds a `json.Number`, and the new test documents that
  exception. The pin stays correct and harmless on that request, so the overbreadth changes
  no behaviour. I treat it as a non-blocking nit.
- **Depth pin on non-recursive reads.** The helper pins the depth on `selectCommit` and
  `selectDurationPrior`. Those statements walk no recursive CTE. The setting is harmless
  there, and T4.5 measured Cloud accepting it.
- **Historical records.** `t4.5-live-probe.md` and `t7.2a-round1.md` name `postClickHouse`.
  They are past review records, so they stay as written.
- **Readiness probe.** `probeClickHouse` in `internal/api` builds its own `GET /ping`. It
  reads no data and decodes no JSON. T7.2b owns that file and that decision.
