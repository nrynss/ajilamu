### M1: The handoff misdescribes the shipped runner

The handoff entry at `dev-diary/PHASE-2-fit-loop.md:763` reads:

> **Not done here.** The runner still builds one synthesizer for the process. `cmd/ajilamu` does
> not build, because `tts.NewSynthesizer(cfg, router, card, nil)` at `cmd/ajilamu/main.go:385`
> uses the old four-argument form. T7.5b owns the fix.

The working tree contradicts every clause. `cmd/ajilamu/main.go:429-431` builds the synthesizer
per run through `newSynthesizer`. `cmd/ajilamu/main.go:452` calls that factory with
`language.tag`. `go build ./...` exits 0. The old four-argument call sat at `main.go:385` at
commit `9258f5c`. That line now sits inside `resolveRunLanguage`.

The contract-change file already records the true state. T7.5b's block also assumes the factory
exists (`dev-diary/PHASE-7-ingestion.md:513`). A next agent that trusts the handoff would rebuild
or revert working code. The handoff is the binding record for the task, so this is a defect rather
than a note.

### M2: The runner wiring has no committed pin

The task's `owns` line now carries `cmd/ajilamu/main_test.go`. No later task carries it. T7.5b
owns `cmd/ajilamu/main.go` and not the test file (`dev-diary/PHASE-7-ingestion.md:500`). T7.7 owns
`cmd/ajilamu/main.go` and not the test file (`dev-diary/PHASE-7-ingestion.md:529`). T2.8b is
therefore the only task that can commit the pin.

The implementer measured the wiring with a throwaway harness and deleted it. The contract-change
file records that deletion and asks the orchestrator to name an owner. The owner now exists. The
committed `TestPipelineLanguageWiring` covers `internal/fit` only. It builds the synthesizer
itself, so it cannot catch a runner that ignores the run language.

Mutation M2 shows the gap. The factory ignores its language argument and always builds `ml-IN`.
`go test -count=1 ./cmd/... ./internal/fit` still passes. An `es-ES` run would then synthesize
Malayalam with no failing check.

## Residue

Three items sit outside this task's verdict. I record them with evidence.

1. **The api event stream carries two codes.** `dubRun.language` copies `req.Language`
   (`internal/api/run.go:377`). The start event and `terminalEvent` stamp that raw code
   (`internal/api/run.go:268-273` and `internal/api/run.go:465-496`). The runner resolves `ml` to
   `ml-IN` in its own copy (`cmd/ajilamu/main.go:446`). The banner renders
   `step.language.toUpperCase()` (`web/src/lib/states/ProcessingBanner.svelte:34`). The label
   flips `ML` to `ML-IN` and back. The contract-change file records the raw-code gap, and T7.5b
   owns the request change. I did not file it, because the fix sits in T7.5b's owns.

2. **The per-run factory leaks one Cloud TTS client per run.** The factory passes a nil client
   (`cmd/ajilamu/main.go:430`). `NewSynthesizer` then calls `newProductionClient`
   (`internal/tts/chirp.go:84-90`). Nothing closes that client. `grep -rn "Close()" internal/tts`
   finds only the WAV file close at `internal/tts/chirp.go:224`. A long-lived server accumulates
   gRPC connections. The fix needs an exported client or a `Close` on the interface. That file is
   T2.8a's owns, so T2.8b cannot fix it without a contract change.

3. **`resolveRunLanguage("ml-IN")` names the code, not Malayalam.** The table keys on the
   create-screen code `ml` (`cmd/ajilamu/main.go:370`). T7.5b plans to send the full tag. T7.5b
   also plans to put the display name on the request. The risk is conditional on that second
   change. The probe logged the value `ml-IN`.
