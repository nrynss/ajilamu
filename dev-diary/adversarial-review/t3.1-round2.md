## Short-gap reproduction

I copied the unchanged production assembler and media helpers into a temporary module.
A small driver called BuildBed and PrepareTake. External tools measured its artifacts.
I selected `/opt/homebrew/bin/ffmpeg` and `/opt/homebrew/bin/ffprobe`, both version 9.0.1.
Go reports version 1.27.1.

Generate a three-second source with a 50 ms timestamp gap after one second of tone:

```sh
ffmpeg -v error \
  -f lavfi -i color=black:s=32x32:r=100:d=3 \
  -f lavfi -i sine=frequency=440:sample_rate=48000:duration=2 \
  -af 'asetnsamples=n=480,asetpts=PTS+gte(T\,1)*0.05/TB' \
  -map 0:v -map 1:a -ac 2 -c:v ffv1 -c:a pcm_s16le shortgap.mkv
```

Call `BuildBed("shortgap.mkv", "", "shortgap-bed.wav")`.
Inspect packet timestamps and the output samples:

```sh
ffprobe -v error -select_streams a \
  -show_entries packet=pts_time,duration_time -of csv=p=0 shortgap.mkv
ffmpeg -hide_banner -i shortgap-bed.wav \
  -af silencedetect=noise=-60dB:d=0.01 -f null -
ffmpeg -hide_banner -ss 1.01 -t 0.03 -i shortgap-bed.wav \
  -af volumedetect -f null -
```

The source has consecutive packet timestamps 0.990000 and 1.050000, each carrying 0.010000 seconds of samples.
That leaves 50 ms without source audio.
The output reports silence only from 2.000000 to 3.000000 seconds.
The expected silent window instead measures -24.1 dB mean and -21.1 dB maximum.
Thus this pin measures misplaced audio, rather than relying on a successful render or filter log.

The installed filter documentation reports `min_hard_comp` defaults to 0.1 seconds.
The current filter leaves that threshold unchanged.
The existing timestamp regression uses a one-second gap, which cannot detect this defect.
